# 共通開発ガイド（AI 向け）

開発全体に共通する運用のルールです。どの開発モデルを採用していても使います。パスは `.github/` からの相対パスです。

## 開発モデル

- 進め方は、リポジトリが採用している開発モデルに従ってください。
- 採用している開発モデルは、各リポジトリの AGENTS.md の「このリポジトリ固有のルール」に書かれています。書かれていない場合は、推測せずに人に確認してください。
- 開発モデルの定義は `docs/design-notes/dev-models/<モデル名>.md` にあります（現在はすべて仮定義です）。

## 担い手

- 作る側（設計・実装・検証）は AI です。設計は Claude、実装は Codex を優先し、その次に Claude Code が担います。
- 決める側（要求、成功条件、重要な制約、大きなトレードオフの判断、採否、承認）は人です。

## 開発の基本姿勢

- 要求から構造を導いてください（トップダウン）。先に部品を作ってから組み合わせ方を考える順にはしません。
- 既存の AI やツールの機能（Claude Code のフック、スキル、サブエージェントなど）で足りるものはそれを使い、足りない部分だけを自作してください。
- レビューの重さは、変更のリスクに合わせてください。複数の AI によるレビューを毎回必須にはしません。

## 人に上げること（どの開発モデルでも）

次の場合は、作業を止めて人に判断を求めてください。

- 作業を続けられない問題が起きたとき
- 取り消せない、または取り消しにくい操作をするとき
- 決まっている要求・仕様・制約から外れる必要が出たとき

人の判断を待つ間も、その判断に依らない作業は進めてかまいません。判断に関わる部分は進めないでください。関わるかどうか迷う部分も進めないでください。

逆に、任された範囲の判断は、人に戻さずに自分で決めて記録してください。任されたかどうか迷う場合は、人に確認してください。

## 作業の委任

- 作業を別の担い手（たとえば窓口の Claude から Codex）に任せるときは、指示書に次を書いてください。
  - 目的
  - 範囲と対象外
  - 読むべき資料（要求、適用する指示）
    - 要求、仕様、ログなどの資料は、指示書に書き写さずに、正本の場所と読むべき箇所を渡してください。
  - 成功条件と確かめ方
  - 決まっている制約
  - 任せる判断の範囲
  - 止まる条件
  - 許可する操作（ファイル編集、Git 操作、外部コマンドの実行など）
  - 返してほしいもの
- 開発モデルの全体を読ませることを前提にせず、作業に必要な条件を指示書に書いてください。
- 形式は固定しません。

## 作業の検証と報告

- 1つの作業は、1つの主な目的を持ちます。無関係な変更を混ぜないでください。
- 作業の結果は、成功条件に照らして確かめてください。
  - 設定が入っていることや、処理がエラーなく終わったことだけで、達成としないでください。使う人の操作から外への影響まで、実際の動きを見て確かめてください。
  - 実際に読み込まれているもの（版、設定、ファイル）が、意図したものかも確かめてください。
- 報告には、変更した内容、主な判断と置いた仮定、検証の結果（何を、どの版で、どの条件で、どの種類の確認（模擬か実物か）で確かめたか）、確かめていないこと、残っている課題を書いてください。版は、コミット前の変更ならその旨を書けば足ります。
- 最新の変更のあとに確かめ直していないものは、そう書いてください。
- 確かめていない動作を、推測で「動く」と書かないでください。
- 検証の結果と人の採否は分けて扱ってください。採用されても、確かめていないことは未検証のまま扱います。

## 設計メモ

判断は設計メモ（議事録の形）に記録します。形式は固定しません。

- 置き場所: 各リポジトリの `docs/design-notes/` に置きます。`.github` 共通のことは `.github` の `docs/design-notes/` に置きます。
- まとめる単位: 作業ごとではなく、機能・部品・横断的な領域ごとにまとめます。同じ対象は、同じメモを更新し続けてください。
- 状態の区別: 決定・提案・委任・実装済みを区別してください。決定には、誰が決めたか（人か、任された範囲での AI か）を書きます。実装済みは、検証済みや承認済みを意味しません。
- AI の判断（理由、検討した代案、置いた仮定）と、人の承認は分けて書いてください。
- 人が承認するまでは、仕様として扱わないでください。
- 人が決めたことは、合意なく変えないでください。AI に任された判断は、その範囲で変えてかまいません。
- 書く量: 残す価値のある判断に絞ってください。コードを見れば分かる細部は書きません。文書は今必要な範囲にとどめます。
- 正本: リポジトリ内のファイルが正本です。コミット前の変更も含め、ローカルの今の内容を正とします。
- 読み方: 作業に必要な設計メモだけを読んでください。全部を読む必要はありません。
- 実装のあと: 実装したら、関係する設計メモが実際の内容と合っているかを確かめ、ずれていれば直してください。
- 正式化: 設計メモは正式な仕様の材料です。そのまま仕様にはしません。

## 承認の求め方

- 人に承認を求めるときは、1つずつ、代案とおすすめを示して相談してください。まとめて承認を求めないでください。

## 参照資料

- 過去のプロトタイプ（`@prototype`）は参照するだけにしてください。仕様として扱わず、使う場合は内容を評価し直して人の承認を得てください。

## 言語

- 人とのやり取りと文書は日本語で書いてください。
- 人が言語を指定したときは、そちらを優先してください。
- コード、パス、コマンド、ログ、エラーメッセージは、訳さずに原文のまま書いてください。
