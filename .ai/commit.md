# コミットのルール（AI 向け）

コミットするときに読む指示です。コミットは人に指示されたときだけ行います（`.ai/git.md`）。

## コミットの単位

1つのコミットは、1つの変更対象に対する1つの目的を表します。

- 単位はファイル数や作業時間ではなく、変更の意味で決めます。
- 複数のファイルを変えていても、1つの変更対象と目的に収まるなら1つのコミットにしてかまいません。
- 独立した変更対象や目的が複数あるなら、コミットを分けます。
- まとめるためだけに、実在しない上位の変更対象を作らないでください。
- 変更対象は、機能、概念、モデル、設定、文書、インフラなどです。変更したファイルそのものを、そのまま変更対象とみなさないでください。

## メッセージの形

```text
<gitmoji> <type>: <件名>

<本文>
```

- 見出し行（1行目）は必須で、形は固定です。本文は任意です。
- gitmoji と type の間は半角空白1つ、type の後はコロンと半角空白1つです。
- scope は使いません。
- 本文を書くときは、見出し行との間に空行を1つ入れます。

## type と gitmoji

type は変更の目的で選びます。拡張子、フォルダ、使ったツールなどの見た目だけで決めないでください。次の11種類に限り、対応する gitmoji を使います。

| gitmoji | type | 意味 |
| --- | --- | --- |
| ✨ | `feat` | 機能の成立・変更 |
| 🐛 | `fix` | 意図した動作・設定への回復 |
| ⚡ | `perf` | 動作を保ったままの性能・効率の改善 |
| 📦 | `build` | 依存関係・ビルド・パッケージ・生成物の変更 |
| ⏪ | `revert` | 過去の変更の取り消し |
| 📝 | `docs` | 文書の内容・定義の成立・変更 |
| ♻️ | `refactor` | 動作を保ったままの内部構造の変更 |
| 💄 | `style` | 意味・動作を変えない見た目や体裁の変更 |
| ✅ | `test` | テストとその仕組みの変更 |
| 👷 | `ci` | CI/CD の自動化の変更 |
| 🔧 | `chore` | リポジトリの保守そのものが目的の変更 |

`chore` は、分類に迷った変更の逃げ場として使わないでください。

## 件名

- 件名は、変更対象に実際に起きた意味や成果を書きます。目的として掲げただけで、そのコミットでは実現していないことは書かないでください。理由の詳しい説明は本文に回します。
- 日本語で、次の形を基本に簡潔に書きます。
  - `○○を<操作>`（変更対象そのもの）
  - `○○の△△を<操作>`（変更対象の一部や一側面）
- `○○` や `△△` はファイル名に限らず、変更の中心になる意味上の対象を書きます。
- 対象の名前は、既存の名前を参考にして同じものだと分かるようにします。意味が伝われば、日本語や自然な略称でかまいません。識別子、ファイルパス、API 名、製品名など、正確さが必要な表記はそのまま使います。
- リポジトリ自身の名前（製品名など）は、リポジトリから明らかな場合は件名に入れません。例: ai-cos で「AI-CoS の製品要求を策定」ではなく「製品要求を策定」。ほかの製品やリポジトリを指していて区別が必要な場合は入れてかまいません。
- コミットメッセージのためだけに、新しい正式名称や呼び方を作らないでください。
- 操作の言葉は、下の「操作の言葉」を優先します。合う言葉がなければ、ほかの言葉を使ってかまいません。

## 言語

- メッセージは日本語が既定です。別の言語を指定された場合はそれに従います。
- 日本語と英字（英単語、略語、製品名、パス、識別子など）の間には空白を入れません。例: 「AI向け」「.githubの共通AI指示」。英字の語どうしの間には空白を入れます。例: 「Claude Code」。件名と本文の両方に当てはめます。
- 定義された用語（開発モデルの名前など）を英語で書くときは、日本語の説明を全角の括弧で添えます。例: 「prototype-first（プロトタイプ先行開発）」。一般の英単語、製品名、パス、識別子には付けません。
- type は言語によって変えません。製品名、識別子、ファイルパスなどは、言語に合わせて訳したり改名したりしないでください。

## 本文

- 見出し行は「何を変えたか」、本文は「そのコミット固有の理由や背景」、差分は「具体的にどう変えたか」を担います。
- 本文は、見出し行と差分からは分からない、残す価値のある情報があるときだけ書きます。
- ファイル一覧、変更箇所の列挙、差分の言い換え、作業の完了報告は書かないでください。
- 書く内容は、次から必要なものだけを選びます。毎回すべてを書く必要はありません。
  1. 背景: 変更の前に、何が問題・不足だったか。
  2. 理由: なぜこの変更が必要か。なぜこの方法にしたか。
  3. 代案: 検討して採らなかった方法と、その理由（判断が分かれる変更のときだけ）。
  4. 影響: 副作用、互換性、残る制約、あとで見直す点。
  5. 参照: 関係する設計メモ、決定、コミット。
- 背景から影響までは、見出しを付けずに文章で書きます。1つの段落に1つの話題を目安にします。
- 読み手が経緯を知らない前提で書きます。設計メモや外部の議論は、参照を示すだけにせず、本文に要点を1文で書きます。
- 参照は本文の最後の段落に、`Refs: <参照先>` の形で1行に1つずつ書きます（Git のトレーラーの形）。参照先は、リポジトリ内のパスなどです（例: `Refs: docs/design-notes/ai-instructions.md`）。

例:

```text
📝 docs: 共通AI指示を策定

各リポジトリのAIが同じ基準で作業できるよう、共通のルールを.githubだけに置く。

Refs: docs/design-notes/ai-instructions.md
```

## AI の関与表記

- `Co-Authored-By:` や `Generated with` など、AI やツールの関与を示す表記は付けないでください。ツールが自動で付けるものも含みます。
- 付けずにコミットする方法がない場合は、コミットせずに人に報告してください。
- コミット後に意図しない表記が見つかったら、コミット ID と表記を報告してください。既存のコミットを直すのは、人に明示的に指示された場合だけです。

## コミットの区切りの提案

- 基本は、1つの作業（1つの目的を持つ作業）が終わり、成果物ができたときに、コミットを提案します。
- ただし、1つの作業が1つのコミットになるとは限りません。作業の途中でも、1つの変更対象と目的がまとまったとき、またはこれから別の変更対象や目的の変更を始めるときは、続ける前に「ここまでをコミットしてはどうか」と、単位とメッセージの案を示してください。
- 提案するだけです。コミットは、下の進め方に沿って人の指示を受けてから行います。

## 直前のコミットへの追加

- 同じ作業の中でコミットを分けたあと、続けた変更が直前のコミットと同じ変更対象・目的に含まれると判断できる場合は、新しいコミットの代わりに、直前のコミットへの追加（`--amend`）を提案してかまいません。分けたコミットを、直後の作業に合わせて直せるようにするための安全策です。
- 対象は直前（最新）のコミットで、まだ push していない場合だけです。それより前のコミットは対象にしません。
- 提案するときは、追加する変更と、追加後のメッセージ（変えない場合はそのまま）を示してください。
- 実行は、「前回に追加して」のような明示的な指示を受けてからにしてください。

## コミットの進め方

1. 実際の差分と検証結果をもとに、コミットの単位を決めます。
2. コミットごとに、変更対象、目的、含める変更、メッセージ、順番をまとめて示し、人の承認を求めます。同じファイルの中で分ける必要があれば、その範囲も示します。直すよう言われたら、直して示し直します。
3. 承認のあと、人が自分でコミットすることがあります。その場合、AI はコミットしません。
4. AI がコミットするのは、承認に加えて、コミットの実行を指示されたときだけです。「これでコミットして」のように、承認と指示を一度に受けてもかまいません。コミットの前に、ステージの状態（`git status`、`git diff --cached`）を確かめ、承認されたコミットの対象と一致しているかを確認します。作業中のステージは人が操作しているので、足りない変更、余分な変更、ステージのあとに変わった変更（`AM` など）がないかを見ます。一致しない場合は、違いを示し、人の承認を得てからステージを変えます。
5. AI がコミットしたときは、コミット後に、コミット ID、実際のメッセージ、含まれた変更、残っている差分を確認して報告します。確認できなかった範囲があれば、そのことを書きます。
6. push は人が行います（`.ai/git.md`）。

## 操作の言葉

推奨の言葉です。これ以外を使ってもかまいません。複数が合う場合は、目的と実際の変化に一番近いものを選びます。

| 意味 | 言葉 |
| --- | --- |
| establish | 策定 |
| revise | 改定 |
| add | 追加 |
| fix | 修正 |
| unify | 統一 |
| align | 整合 |
| build | 構築 |
| apply | 適用 |
| update | 更新 |
| improve | 改善 |
| restructure | 再構成 |
| format | 整形 |
| remove | 削除 |
| revert | 取り消し |
| rename | 改称 |
| migrate | 移行 |

## 例

```text
✨ feat: 知識登録機能を追加
🐛 fix: 検索結果の重複を修正
♻️ refactor: 知識保存処理を再構成
📝 docs: 共通開発方針を策定
```
