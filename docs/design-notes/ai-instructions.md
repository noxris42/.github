# 設計メモ: AI 指示系統

状態: 議事録（正式な仕様ではありません）。AI に読ませる指示文書（AGENTS.md と `.ai/` 以下）の仕組みについて、決まったことと、その理由をまとめます。

- 書き方: 決定には、誰が決めたか（人か、任された範囲での AI か）を書きます。AI の判断（理由、代案、仮定）と人の決定は分けて書きます。
- 経緯の番号（U1、S2-U9 など）は、ステップ1・2のやり取りで付けた番号です。
- 開発モデル（prototype-first）そのものの経緯は、`dev-models/prototype-first.md` の改善履歴に書きます。

## 1. 入口と読み込み

### 決定

- 入口は AGENTS.md だけにし、CLAUDE.md は置きません（人が決定。U1、U4）。
- 各リポジトリは、自分の AGENTS.md から `../.github/AGENTS.md` を読んで共通の指示を取り込みます（人が決定。U5）。
- パスは相対パスで書き、各リポジトリと `.github` が同じ親フォルダに並んでいる前提にします。GitHub の URL への逃げ道は入れません（人が決定。U2。AI の判断 A4）。
- 指示文書どうしの参照に `@`（Claude Code の取り込み構文）は使わず、文章で相対パスを書きます（人が決定。U6）。
  - 人の理由: AGENTS.md はどの AI も読む入口なので、特定のツールの構文に頼らない。
- AI-CoS は Claude Code（窓口）の上で、Claude プラグインとして動かします（人が決定。U9）。
  - 人の理由: Claude の非対話呼び出しはサブスクリプション枠での扱いが不安定。窓口を固定すれば、Claude の機能（フック、スキルなど）を前提に設計できる。
  - 区別: 「Claude Code で動くこと」と「ほかの AI が指示文書を理解できること」は別です。Codex などが読む指示文書は、汎用の書き方のままにします。

### 確かめたこと（Claude Code 2.1.326、クラウド環境、2026-11-17）

- CLAUDE.md が無いと、AGENTS.md が自動で読み込まれる。両方あると CLAUDE.md だけが読まれる。公式ドキュメントには無い挙動です。
- `@` なしの文章の参照でも、作業を伴う依頼では AI が2段の参照を自分で読みに行った。作業を伴わない質問では読まなかった。
- Codex、Gemini では未検証です。

### 引き受けたリスク

- AGENTS.md の自動読み込みは公式の挙動ではないので、Claude Code の版が上がったら確かめ直します。空の CLAUDE.md を置くと AGENTS.md が読まれなくなります。
- 参照先を読むかどうかは AI 任せです。必要なら、AI-CoS の窓口が依頼のときに読むべき文書を明示して補います。
- Claude Code の仕様変更の影響を直接受けます。窓口の利用分は Claude の枠を使います。

## 2. 層の構造と正本

### 決定（人が決定。U10、U11）

- `.github` が共通のルール・規定・規約を持ちます（正本）。ほかのリポジトリに同じ内容を書き写しません。例外は、雛形から写す「.github への接続手順」だけです。
- 3つの層に分けます。
  - 層0 `各リポジトリ/AGENTS.md`: `.github` への接続手順（雛形 `.github/.ai/templates/consumer-AGENTS.md` の写し）と、そのリポジトリ固有のルール。
  - 層1 `.github/AGENTS.md`: どの作業でも守る前提ルールと、状況ごとに読むファイルの表。
  - 層2 `.github/.ai/*.md`: 状況ごとの詳細（development.md、git.md、commit.md など）。
- AI 向けの指示文書は `.github/.ai/` に置きます（人が決定。U7）。
  - 人の理由: `.claude` などほかの AI ツールのフォルダとそろう。人向けの文書と分けられる。
  - 取り決め: `.ai/` には AI 向けの指示文書だけを置きます。過去のプロトタイプの作業データ用 `.ai-cos/` とは別物です。
- 前提ルールに入れる基準: どの作業にも当てはまり、行動の前に知っていないと効かないものだけを、短く書きます（S2-U9 で言い直し）。文字コードは「先に知らないとほかのファイルを読めない」特殊な例です。

### AI の判断

- 雛形の写しに「直接編集せず、雛形を直してから写し直す」という注記を入れました。雛形は AI 向けの指示文書の一部なので `.ai/templates/` に置きました。
- `.github/AGENTS.md` と `.ai/` のパスは「`.github/` からの相対パス」と明記しました。Codex などはパスを自分で解釈するためです（A6）。

### 根拠にした情報

- Claude Code の公式ドキュメント: 毎回読むファイルは 200 行未満が目安。分割して取り込んでもコンテキストの量は減らない。絶対に守らせたいことは、フックや権限設定で機械的に止める。

## 3. シェルと文字コード

### 決定（人が決定。U3、U8）

- Windows の既定のシェルは PowerShell 7（`pwsh`）にします。
- 文書は UTF-8（BOM なし）・改行 LF です。読み書きでは UTF-8 を明示し、外部 CLI とテキストをやり取りする前に、コンソールの入出力を UTF-8 にします。

### AI の判断と理由

- 文字化けの原因: Windows PowerShell 5.1 の `Get-Content` は、BOM なしの UTF-8 を CP932 として読みます。AI がシェル経由で読むと、化けた指示を受け取ります。
- `pwsh` はファイルの読み書きの既定が UTF-8 なので、主な原因は消えます。ただし `[Console]::OutputEncoding` は OS のコードページ（CP932）のまま残るので、その設定の1行は必要です。
- 仮定（未検証）: Codex などがシェルに `pwsh` を使うかは、ツール側の設定次第です。5.1 で動いた場合は `-Encoding utf8NoBOM` がエラーになるので、気づきやすくなります。
- `.editorconfig`、`.gitattributes` は、文字化けが実際に起きたら検討します。

## 4. Git の操作

### 決定（人が決定。S2-U9）

- 禁止の核（人の指示なしに Git の状態を変えない。読み取りは可。状態を変える前に `.ai/git.md` を読む）だけを `.github/AGENTS.md` の前提ルールに置き、詳細は `.ai/git.md` に分けます。
  - 経緯: AI は、Git の決まりを全部 AGENTS.md に置く案を出しました。人が「Git 操作のときだけ読む形に当てはまらないか」と指摘しました。
  - AI の整理: 禁止は、行動を決める前に知っていないと効きません（思いつきの stash や restore には、読むきっかけがありません）。だから核は常に読む場所に置き、細目は必要なときに読む形にしました。
- AI は、人に指示されたときだけコミットします。
- push は人だけが行います（人が決定。S2-U34）。最後の安全装置です。運用が安定したら、AI に頼めるようにする可能性があります。

### AI の判断

- 指示があっても、取り消せない操作（reset --hard、clean、force push など）は、対象を示して確認してから行う、を `.ai/git.md` に加えました。

### 運用の前提

- 人は、AI の変更を自分でステージして、差分を目で確かめています。AI はステージに触れません。

## 5. コミット

### 決定（人が決定。S2-U10、S2-U11）

- 過去のプロトタイプ v3 のコミットメッセージの形式（gitmoji ＋ type ＋ 日本語の件名、1つの変更対象×1つの目的、本文は理由、AI の関与の表記なし）を引き継ぎます。試行錯誤で積み上げたものです。
- 件名には、リポジトリから明らかな場合、そのリポジトリ自身の名前（製品名）を入れません。絶対の禁止ではありません。
- コミットの運用（人が決定。S2-U31〜S2-U34）:
  - AI が単位とメッセージを示し、人が承認します。コミットは人が行うか、承認と実行の指示を受けて AI が行います。
  - コミットの単位は作業でもあります。作業は基本1つの目的で、終われば成果物ができるので「作業の完了＝コミット」が基本形です。ただし1作業＝1コミットではなく、作業の途中でも区切りを提案します。
  - 直前のコミットへの追加（amend）は、同じ作業の中で分けたコミットを、直後の作業に合わせて直すための安全策です。直前かつ未 push のコミットだけを対象にし、明示的な指示で行います。
  - コミットのときは、AI がステージの状態を確かめ、コミットの対象と一致しているかを確認します。違いがあれば示し、人の承認を得てからステージを変えます（S2-U36）。作業中のステージは人が操作します。
- コミットメッセージでは、日本語と英字の間に空白を入れず、英字の語どうしの間には入れます（人が決定。S2-U35）。定義された用語を英語で書くときは「prototype-first（プロトタイプ先行開発）」のように日本語の説明を添えます（人が決定。S2-U37）。どちらも後から直しにくいので今から守ります。文書の体裁は今は問わず、将来の文書規約で定めます。
- コミットメッセージの本文（人が決定。S2-U38）: Git の投稿ガイドや Chris Beams の指針を参考に、背景・理由・代案・影響・参照から必要なものを選んで書きます。具体的なやり方（How）は差分に任せます。背景から影響までは見出しなしの文章、参照は末尾に `Refs:` のトレーラーで書きます。GitHub の Issue との連携は、連携するときに決めます。
- 採らなかった AI の改善案: メッセージをファイル経由で渡す、AI 指示文書の type の決まり、複数リポジトリにまたがる変更の書き方。いずれも、今は問題が起きていないためです。

## 6. 開発の運用（development.md）

### 決定（人が決定。S2-U5〜S2-U7、S2-U12〜S2-U18、S2-U24〜S2-U30）

- 開発モデル（進め方）と運用（誰が何を担うか）を分けます。開発モデルは担い手を書かず、AI と人の役割分担は development.md に書きます。
- 開発モデルは各リポジトリの AGENTS.md の固有ルールで指定し、`docs/design-notes/dev-models/<モデル名>.md` に仮定義として置きます（S2-U3）。正式化したら、正式な定義として別の場所に置きます。
- development.md に置いたもの: 担い手（決める側に成功条件・重要な制約・大きなトレードオフの判断を含む）、開発の基本姿勢、人に上げること（判断待ちの間の進め方、任された判断は戻さない）、作業の委任、作業の検証と報告、設計メモ、承認の求め方、参照資料、言語。
- 過去のプロトタイプ v3 との差分を1つずつ見直しました（S2-U8）。v3 の知見は「知見として写す」のではなく、今回の運用ルールに取り入れました（S2-U24）。
- 入れなかったもの:
  - 製品固有の作り方を共通ルールにしない基準（S2-U29）。今は、何を共通にするかを人が判断しているためです。蓄積から自動化に近い仕組みができたら必要になります。
  - 利用枠の測り方や試験の組み方など、AI-CoS の検証そのものの話。
