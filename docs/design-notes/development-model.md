# 開発モデル — 暫定方針

状態：実践開始前・未検証の暫定モデル。記録日：2026-11-02。

本書は、最小要求からAIへ設計・実装・検証を委任し、成果の評価から要求・仕様を段階的に明確化する構想を記録する。モデルの完成や正式規約化を意味しない。

適用する共通指示は[共通開発指示](../development.md)を参照する。本書はそのRequirements-first、AI-delegated Design、Just-in-time Design、Prototype-firstを具体化する暫定方針であり、指示の入口・適用方式を変更しない。実装AIへの読み込みを一律必須とせず、必要な運用条件を個別の指示書へ落とし込む。

## 構想と役割

実装からのフィードバックで仕様を育てる、反復型の仕様書駆動開発を目指す。

人間との対話で目的と要求の全体像を描き、コアとなる最小要求からAIへ委任する。動作する成果物とAIの判断記録を材料に、要求・設計・仕様を明確化して次の実装へ反映する。最初から完全な仕様を求めず、要求・設計・実装を厳密なフェーズで区切らない。確定している方式や構造は最初から含めてよい。

着想として、AMDDの必要な分だけ要求・設計を具体化する考え方と、仕様書駆動開発の仕様を継続資産として保持する考え方を参考にする。両手法の詳細な定義や手順の採用を意味せず、特定ツールの採用も未決定である。

人間は目的・要求・成功条件・重要な制約、重大な選択、成果の採否を担う。ChatGPTは対話による明確化、Task管理、委任条件の整理、成果評価を支援する。実装AIは委任範囲内の設計・実装・実行・検証・修正と、重要な判断の記録を担う。担当AIやツールはTaskに応じて選ぶ。

## 基本サイクル

1. 対話で目的、利用場面、期待する能力、制約、未確定事項を整理する。
2. コアとなる価値と、成立を確認したい不確実性を評価できる最小モデルを選ぶ。
3. AIへ設計・実装・実行・検証・修正を委任する。
4. 人間が実物、検証結果、主要な設計判断を評価する。
5. 採用した判断と得られた知見を要求・仕様へ反映する。
6. 次の追加検証・改修・拡張・再生成・終了を選ぶ。

各活動は必要に応じて行き来する。初回実装後にアーキテクチャを確定するなど、反復の順序を固定しない。

## 委任条件とアウトプット

実装AIがモデル全体の思想を理解することを作業の前提にしない。個別の指示書には、読むべき要求資料、適用するRepositoryの指示、目的、範囲、成功条件・確認方法、固定制約、対象外、委任範囲、停止条件、操作の許可範囲を渡す。

アウトプットとして次を求める。

- 動作する成果物と起動・操作方法。
- 要求ごとの達成・未達成・未検証と、検証方法・結果。
- 主要な設計判断と理由、重要な代替案と影響。
- AIが補った仮定、制約、既知の問題、確認事項。

通常の内部設計はAIへ委任し、逐一承認を求めない。要求・成功条件の変更、固定制約からの逸脱、委任範囲を超える重大な選択は人間へ確認する。作業継続を妨げる問題や停止条件に該当する場合は、状況と判断に必要な情報を報告する。

判断記録は重要度に応じて絞り、コードから容易に分かる細部を重複記録しない。重要な設計情報は共通指示に従って関連するDesign Notesへ反映し、固定テンプレートや専用ツールは要求しない。

## 評価と仕様更新

AIが実装した内容を、自動的に正式仕様へ昇格させない。評価結果は、採用する要求・判断、暫定的な選択、保留・未検証事項、変更・延期する事項として整理する。

人間による採否と検証状態は別に記録する。承認によって未検証の動作を検証済みとは扱わない。内部構造のすべてを個別承認・固定する工程にはせず、委任範囲内の技術判断はAIが行い、必要に応じて変更する。

共通指示のDecided / Proposed / Delegated / Implementedは設計判断・実装状態を表す。これらだけから人間の承認や検証完了を推定せず、必要な採否と検証結果を併記する。新たな固定状態管理Schemaは設けない。

評価結果に応じて改修と再生成を選ぶ。再生成する場合も、要求、検証方法、採用済みの判断、得られた知見を引き継ぐ。

## Repositoryの責務

| Repository | 保持する情報 |
| --- | --- |
| `.github` | 開発モデルの暫定方針、実践から得た再利用可能な知見、改善履歴、最終的な正式ドキュメント |
| `ai-cos` | AI-CoS固有の要求・仕様・設計判断・実装・検証結果 |
| `symnous` | Symnous固有の要求・仕様・設計判断・実装・検証結果 |

製品固有の事実と、別の開発へ再利用できる知見を分けて保持する。必要な情報は各Repositoryの本文へ取り込み、チャット参照だけに依存させない。本書はモデル単位で継続更新し、正式化に至るまでは共通指示のDesign Notesとして扱う。

## モデルの育成と今後の確認

まずAI-CoSの開発を通じてモデルを形成し、次にSymnousの開発で再現・改善する。その結果を再評価して`.github`へ正式ドキュメント化し、以後も実践結果に基づいて更新する。

再現性とは、同じコードを生成することではなく、別の開発でも同じ進め方で不確実性を減らし、評価可能な成果へ到達できることを意味する。

各反復で、次を短く振り返り、再利用できる知見と改善履歴を本書へ追記する。製品固有の検証結果は製品Repositoryに保持する。

- 入力した要求と委任条件で、AIが適切に進められたか。
- 成果物・検証結果・判断記録で、人間が採否を判断できたか。
- 次回の入力や記録方法をどう改善するか。

本書に記録した進め方を試行方針とし、その有効性は今後の実践で確かめる。特に、最小モデルの選び方、委任・停止条件の十分さ、記録の適量、評価から仕様更新への接続、改修と再生成の選択、別製品での再現性は未検証である。詳細手順、固定テンプレート、専用ツールは必要性が明らかになってから判断する。
