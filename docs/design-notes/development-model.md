# 開発モデル — 暫定方針

状態：AI-CoSで初回実践済み・別製品での再現性は未検証の暫定モデル。初版：2026-11-02。更新日：2026-11-06（日本時間）。

本書は、最小要求からAIへ設計・実装・検証を委任し、成果の評価から要求・仕様を段階的に明確化する構想を記録する。モデルの完成や正式規約化を意味しない。

適用する共通指示は[共通開発指示](../development.md)を参照する。本書はそのRequirements-first、AI-delegated Design、Just-in-time Design、Prototype-firstを具体化する暫定方針であり、指示の入口・適用方式を変更しない。実装AIへの読み込みを一律必須とせず、必要な運用条件を個別の指示書へ落とし込む。

## 構想と役割

実装からのフィードバックで仕様を育てる、反復型の仕様書駆動開発を目指す。

人間との対話で目的と要求の全体像を描き、コアとなる最小要求からAIへ委任する。動作する成果物とAIの判断記録を材料に、要求・設計・仕様を明確化して次の実装へ反映する。最初から完全な仕様を求めず、要求・設計・実装を厳密なフェーズで区切らない。確定している方式や構造は最初から含めてよい。

着想として、AMDDの必要な分だけ要求・設計を具体化する考え方と、仕様書駆動開発の仕様を継続資産として保持する考え方を参考にする。両手法の詳細な定義や手順の採用を意味せず、特定ツールの採用も未決定である。

人間は目的・要求・成功条件・重要な制約、重大な選択、成果の採否を担う。ChatGPTは対話による明確化、Task管理、委任条件の整理、成果評価を支援する。実装AIは委任範囲内の設計・実装・実行・検証・修正と、重要な判断の記録を担う。担当AIやツールはTaskに応じて選ぶ。

## 基本サイクル

1. 対話で目的、利用場面、期待する能力、制約、未確定事項を整理する。
2. コアとなる価値と、成立を確認したい不確実性を評価できる最小モデルを選ぶ。
3. AIへ設計・実装・実行・検証・修正を委任する。
4. 人間が実物、検証結果、主要な設計判断を評価する。
5. 採用した判断と得られた知見を要求・仕様へ反映する。
6. 次の追加検証・改修・拡張・再生成・終了を選ぶ。

各活動は必要に応じて行き来する。初回実装後にアーキテクチャを確定するなど、反復の順序を固定しない。

## 委任条件とアウトプット

実装AIがモデル全体の思想を理解することを作業の前提にしない。個別の指示書には、読むべき要求資料、適用するRepositoryの指示、目的、範囲、成功条件・確認方法、固定制約、対象外、委任範囲、停止条件、操作の許可範囲を渡す。

アウトプットとして次を求める。

- 動作する成果物と起動・操作方法。
- 要求ごとの達成・未達成・未検証と、検証方法・結果。
- 主要な設計判断と理由、重要な代替案と影響。
- AIが補った仮定、制約、既知の問題、確認事項。

通常の内部設計はAIへ委任し、逐一承認を求めない。要求・成功条件の変更、固定制約からの逸脱、委任範囲を超える重大な選択は人間へ確認する。作業継続を妨げる問題や停止条件に該当する場合は、状況と判断に必要な情報を報告する。

判断記録は重要度に応じて絞り、コードから容易に分かる細部を重複記録しない。重要な設計情報は共通指示に従って関連するDesign Notesへ反映し、固定テンプレートや専用ツールは要求しない。

## 評価と仕様更新

AIが実装した内容を、自動的に正式仕様へ昇格させない。評価結果は、採用する要求・判断、暫定的な選択、保留・未検証事項、変更・延期する事項として整理する。

人間による採否と検証状態は別に記録する。承認によって未検証の動作を検証済みとは扱わない。内部構造のすべてを個別承認・固定する工程にはせず、委任範囲内の技術判断はAIが行い、必要に応じて変更する。

共通指示のDecided / Proposed / Delegated / Implementedは設計判断・実装状態を表す。これらだけから人間の承認や検証完了を推定せず、必要な採否と検証結果を併記する。新たな固定状態管理Schemaは設けない。

評価結果に応じて改修と再生成を選ぶ。再生成する場合も、要求、検証方法、採用済みの判断、得られた知見を引き継ぐ。

## モデルの育成と今後の確認

まずAI-CoSの開発を通じてモデルを形成し、次にSymnousの開発で再現・改善する。その結果を再評価して`.github`へ正式ドキュメント化し、以後も実践結果に基づいて更新する。

再現性とは、同じコードを生成することではなく、別の開発でも同じ進め方で不確実性を減らし、評価可能な成果へ到達できることを意味する。

各反復で、次を短く振り返り、再利用できる知見と改善履歴を本書へ追記する。製品固有の検証結果は製品Repositoryに保持する。

- 入力した要求と委任条件で、AIが適切に進められたか。
- 成果物・検証結果・判断記録で、人間が採否を判断できたか。
- 次回の入力や記録方法をどう改善するか。

本書に記録した進め方を試行方針とする。AI-CoSでの初回結果は以下に記録するが、最小モデルの選び方、委任・停止条件の十分さ、記録の適量、評価から仕様更新への接続の一般的な有効性は未確立である。改修と再生成の比較、別製品での再現性も未検証である。詳細手順、固定テンプレート、専用ツールは必要性が明らかになってから判断する。

## 初回実践から得た知見（2026-11-06）

対象はAI-CoS初期Prototypeの要求整理から0.2.4採用まで。一つの製品・本人のWindows環境での実践であり、一般的な有効性や開発期間の短縮率を実証したものではない。根拠はai-cosのREADME、docs/design-notes/{overview,prototype,cos-plugin}.md、docs/verification/prototype-v0.1.mdおよび振り返りTaskへの引継ぎ。実機の再実行や全ログの再監査は行っていない。製品固有の版別結果はai-cosに保持し、本節には再利用するための必要情報を取り込む。

### 記録から確認できたこと

| 評価点 | 初回で確認した事実 | 解釈・適用限界 |
| --- | --- | --- |
| 全体像と初回要求の分離 | 全体構想を保持しながら、一つの利用先・一つの会話・直列の小さな開発に限定。共有記憶・並列・他AI追加などは採用の必須条件にしなかった | 最小範囲の選定に役立ったと考える。分離しない場合との比較はしていない |
| 要求からの具体化 | 価値・成功条件・制約・委任と停止条件・アウトプットを渡し、AIが配置・文脈受渡し・制御・記録形式・検証を具体化した。公式Subagentや初回連携先など、事前に定めた構成制約もあった | 完全な詳細設計の事前確定なしに制作を進められた一例。入力だけで無対話に完成したわけではなく、人間の要求変更・計画修正・試験承認を含む |
| 採否の判断材料 | 人間は既定入口の使い勝手と、成果・失敗・修正・再検証・操作範囲・残事項を示す報告に問題なしと評価し、最終的にPrototypeを採用した | 主要判断と条件別検証が採否に使われた。内部方式すべての承認や、長期運用への十分さを意味しない |
| 限定した誘発試験 | 通常の一周で発生しなかった担当の回答と差戻しを、委任済み技術質問・一件の未実装を誘発して実CLIで確認。担当が試験で未達を特定し、修正後に再検証した | 待つだけでは見えない往復を確認できた。担当は未達の存在を知っていたため、未知の不具合を自然に発見する能力の実証とは分ける |
| 実物による前提の更新 | 標準UIの停止と外部処理の停止は一致せず、試験配置によって操作範囲の確認も無効になった。表示版と実際の読込版にも差があった | 名目の設定や正常終了だけでは要求達成を評価できない。使用者の操作から外部への影響まで観測する必要があった |
| 中継と消費 | 一周内部の手動貼付けは不要。一方、内部担当の重複読込と試験評価のための外部中継は残った。時間・依頼回数・取得可能なusageは記録したが、消費を試験分へ完全に分離できなかった | 手動中継の削減は確認できたが、利用枠の削減率・開発速度の改善率は評価できない |

### 次の反復で試す改善案

以下は担当AIの提案であり、正式規約や固定テンプレートではない。個別Taskに必要な部分だけを採用し、製品固有の実装方式を共通ルールにしない。

- 事前に決めること：評価したい価値、成功条件、保護する対象、許容する制約、要求として人間に戻す未決定事項、操作・外部実行の許可範囲。試験の版・配置・条件が何を確認できるかを短く点検する。
- AIへ任せること：その範囲内の構成、技術選択、文脈と状態の表現、検証・差戻し・再検証。委任済みの技術事項を人間の未決事項へ戻さず、担当の検証責務を計画に明示する。初回ではこれが逆の計画になり、人間の修正が必要だった。
- 求める記録：要求と判断者、主要な理由・仮定、実装した版、実際の読込元と読込版、検証した版・方法・条件・結果、人間の採否と許容した制約を対応させる。Commit前の実装を試した場合も、後のCommitだけから検証対象を推定しない。
- 検証の更新：現行の集約結果と過去の版別結果を分ける。最新版で再実測していない項目を明記し、変更の影響に応じて必要な再確認を選ぶ。模擬・実機・誘発・自然発生と、終了・成果確認・人間の採否を混同しない。
- 情報の受渡し：要求本文や全ログを担当ごとに再生成せず、正本と必要な参照先を渡す。ただしパスで渡すだけでは各担当の再読込は減らない。次回は必要な担当だけが必要な資料を読み、検証に必要な独立確認を残しつつ、重複した確認と報告を減らせるか観察する。

### 別製品・実利用で確認する仮説

| 仮説 | 次に確認したいこと |
| --- | --- |
| 全体像と最小要求の分離が別製品でも有効 | Symnousなどでも、将来要求を失わず評価可能な一周へ絞れるか。要求定義自体は別Taskで行う |
| 委任条件の明示で確認と手戻りを減らせる | 人間へ戻す判断とAIへ任せる判断を分け、実務で不必要な質問・計画修正が減るか |
| 主要判断と条件別の結果で採否を判断できる | 誘発なしの実務でも、報告から未達・未検証・許容する制約を判断できるか。記録不足と過剰記録の両方を観察する |
| 段階的な試験で利用枠の負担を抑えられる | 模擬と小さな実測を組み合わせ、重複確認を減らしても必要な保証が残るか。測れる範囲の時間・回数・usageと人間の負担で比べ、tokenからサブスク残量を推定しない |

初回は改修を重ねて採用へ到達したが、再生成との比較はない。Plugin、Hook、独自ラッパー、特定モデルや非公式形式への依存を、他製品の標準方式にしない。次の実務一件で価値と負担を評価し、必要な一点の改善を選ぶ進め方を候補とする。
